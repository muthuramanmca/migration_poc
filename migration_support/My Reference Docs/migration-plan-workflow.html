Migration Plan - Spec First, Then Code

This is a proof of concept: a synthetic Spring Boot API stands in for United's real booking platform, since no live codebase exists yet. The plan itself doesn't change when that does — the same steps carry over to the real migration, one bounded domain at a time — Identity, Flight, Booking, Loyalty, Notification — so nothing is ever a big-bang cutover, and a wrong assumption gets caught on paper, while it's still cheap to fix, not after it's shipped.

How a slice moves, start to finish

Seven Phases, Two Loops

Phases 01 and 02 set up the whole app once. Everything from 03 onward is a loop that repeats per domain, in whichever dependency order 02 fixed — so a slice never starts drafting before what it depends on already exists to build against.

01
Runs once Automated
Setup .NET Skeleton

Solution layout, conventions, and cross-cutting scaffolding — decided once, for every service that follows.

02
Runs once Automated
Create Java API Contract

Extract the OpenAPI contract from java-api, group its routes into slices, and order those slices by dependency.

03
Runs per slice
Java API, Slice-Wise

Understand a slice's behavior before anyone writes a line of C#.

03_01 Draft spec Automated → 03_02 Sign off Manual gate

Repeats independently for every slice — each domain moves through this loop on its own timeline, not all five at once.

04
Runs per slice, once approved
.NET API Slice Develop

Turn an approved spec into reviewed, tested .NET code.

04_01 Design note Automated → Approve design Manual gate → 04_02 Generate code Automated → 04_03 Write tests Automated → 04_04 Compare vs Java Automated → 04_05 Code review Manual gate

No code is generated until the design note is approved — the same "cheap to fix on paper" logic as the spec gate. Tests are then prompted from the spec, not the generated code, so they can't rubber-stamp a bug the rewrite introduced.

05
Runs once, after slices exist Partial-manual
Cross-Cutting & Integration

Shared auth, error envelope, correlation IDs, inter-service calls — re-tested once enough slices exist to wire together.

06
Runs once, before cutover Partial-manual
Validation Strategy

Contract diff against the Java spec, shadow traffic, and a load/perf baseline before anyone trusts the new stack.

07
Runs per slice Manual gate
Cutover

Module-by-module traffic shift at the gateway. Java stays live as fallback through a soak period.

Automated — Claude drafts it, nothing to type by hand Partial-manual — generatable in part, human coordination for the rest Manual gate — a human has to act before anything moves on
Why it's built this way

Strangler Fig, Spec First

Strangler Fig, not big-bang

The Java app keeps running the whole time. Each domain gets rebuilt in .NET Core behind the same gateway route prefix, then only that domain's traffic is cut over. A defect in one freshly migrated slice never takes four still-healthy ones down with it.

One slice, fully proven, before the next

A slice is a full vertical — Controller → Service → Repository → Entity — not a whole architectural layer. One domain is migrated, tested, and signed off end-to-end before the next domain's spec even starts drafting, so a wrong assumption surfaces while it's still cheap to fix.

Why this approach, in short

Migration Highlights

AI used end-to-end, not just codegen

Specs, design notes, tests, and Java/.NET comparisons are all drafted by Claude — code generation is one step of five, not the whole job.

Cost savings

Most artifacts are generated, not billed as manual engineering hours — spec-writing and test-writing included.

Effort savings

Engineers review and approve; they don't hand-write boilerplate or re-discover business rules buried in old code.

Mistakes caught on paper

A misread business rule costs a paragraph edit in a spec. Caught after code exists, the same mistake costs a rewrite — and a production incident to find it.

Controlled migration, manual gates

Four checkpoints — spec approval, design approval, code review, cutover — keep every AI-generated step accountable to a human.

Migration happening gradually

One domain cuts over at a time; the old system keeps running until each one is proven — never a single high-stakes flip.
